# DESIGN.md

## Overview

This project implements an AI-powered Store Intelligence System that converts raw CCTV footage into structured behavioral events and exposes store analytics through a production-aware API.

The system starts with CCTV clips from multiple camera angles. A YOLOv8-based detection pipeline identifies people in each frame, tracks them using ByteTrack, maps their position into camera-specific store zones, and emits structured behavioral events such as `ENTRY`, `EXIT`, `ZONE_ENTER`, `ZONE_EXIT`, `ZONE_DWELL`, `BILLING_QUEUE_JOIN`, and `PURCHASE`.

These events are ingested by a FastAPI backend, stored in SQLite, and used to compute real-time store metrics including unique visitors, conversion rate, average dwell time, funnel progression, heatmap scores, queue anomalies, and feed health.

The main goal of the system is to answer offline retail questions that are usually easy in online analytics but difficult in physical stores, such as:

* How many customers visited the store?
* How many customers converted into buyers?
* Which store zones received the most attention?
* How long did customers dwell in each zone?
* Is the billing queue building up?
* Is the camera/event feed healthy?

## Architecture

The system is split into four main layers:

```text
Raw CCTV Videos
    ↓
Detection Pipeline
    ↓
Structured Event Files
    ↓
FastAPI Intelligence API
    ↓
Live Streamlit Dashboard
```

## Detection Pipeline

The detection pipeline is implemented in `pipeline/detect.py`.

It uses YOLOv8 for person detection and ByteTrack for tracking. Each tracked person receives a visitor token such as `VIS_1`, `VIS_2`, etc. For each detected person, the pipeline calculates the center point of the bounding box and checks which configured zone contains that point.

The pipeline emits structured events into JSONL files. Each line in the JSONL file is one event.

Example event types generated by the pipeline:

* `ENTRY`
* `EXIT`
* `ZONE_ENTER`
* `ZONE_EXIT`
* `ZONE_DWELL`
* `BILLING_QUEUE_JOIN`

The pipeline also supports POS-derived purchase events through a separate script, `pipeline/generate_purchase_events.py`.

## Camera-Wise Zone Configuration

Initially, the pipeline used one hardcoded zone layout for all camera videos. This did not work well because each CCTV camera has a different angle and coordinate system.

To fix this, the project uses camera-wise zone configuration from:

```text
data/camera_zones.json
```

Each camera has its own zone boundaries and entry line.

Current camera mapping:

```text
CAM_ENTRY_01    → CAM 3 - entry.mp4
CAM_ZONE_01     → CAM 1 - zone.mp4
CAM_ZONE_02     → CAM 2 - zone.mp4
CAM_BILLING_01  → CAM 5 - billing.mp4
```

This makes the detection pipeline more flexible and prevents a billing-camera zone configuration from incorrectly affecting an entry camera or zone camera.

## Store Layout Usage

The provided Store 1 and Store 2 layout PNGs were used as visual references to understand the physical store structure.

The layouts helped identify:

* Entrance location
* FOH customer browsing area
* Billing/cash counter area
* Product display zones
* BOH/non-customer area
* Camera coverage assumptions

The detection pipeline does not run inference directly on the layout PNGs. YOLOv8 runs on CCTV video frames. Since each CCTV camera has its own perspective, the runtime zone boundaries are defined using CCTV frame coordinates in `data/camera_zones.json`.

A separate file documents how the layout images conceptually map to runtime zones:

```text
data/store_layout_reference.json
```

The high-level mapping is:

```text
ENTRY_ZONE  → entrance and entry-facing movement region
MAIN_FLOOR  → FOH customer browsing and product display area
BILLING     → cash counter and billing queue region
```

## Event Schema

Each event follows a consistent schema so the API can ingest detection events and purchase events through the same endpoint.

Example:

```json
{
  "event_id": "uuid",
  "store_id": "STORE_BLR_002",
  "camera_id": "CAM_ZONE_01",
  "visitor_id": "VIS_1",
  "event_type": "ZONE_DWELL",
  "timestamp": "2026-03-03T14:00:30Z",
  "zone_id": "MAIN_FLOOR",
  "dwell_ms": 30000,
  "is_staff": false,
  "confidence": 0.85,
  "metadata": {
    "queue_depth": null,
    "sku_zone": "MAIN_FLOOR",
    "session_seq": 2
  }
}
```

The `event_id` is globally unique and is used for idempotency during ingestion.

The `visitor_id` identifies the tracked visitor within a camera stream.

The `event_type` determines how the event is used by metrics, funnel, heatmap, and anomaly logic.

The `metadata` object stores extra event details such as queue depth, SKU zone label, session sequence, order ID, and transaction amount.

## Event Ingestion

Events are sent to the backend through:

```text
POST /events/ingest
```

The ingest endpoint accepts event batches and stores them in SQLite.

Important ingestion behavior:

* Events are deduplicated using `event_id`
* Replaying the same file does not duplicate rows
* Events are validated through Pydantic models
* Malformed events can be reported through structured errors
* The endpoint supports batch ingestion from JSONL files

The ingestion helper script is:

```text
pipeline/send_events.py
```

## API Layer

The backend is implemented with FastAPI.

Main endpoints:

```text
POST /events/ingest
GET /stores/{store_id}/metrics
GET /stores/{store_id}/funnel
GET /stores/{store_id}/heatmap
GET /stores/{store_id}/anomalies
GET /health
```

SQLite is used for local reproducibility. It is lightweight, easy to inspect, and suitable for a challenge environment. In a production deployment, SQLite could be replaced by PostgreSQL or a streaming analytics store.

## Metrics Logic

The `/stores/{store_id}/metrics` endpoint computes:

* Unique visitors
* Converted visitors
* Conversion rate
* Average dwell time per zone
* Current queue depth

Staff events are excluded from customer metrics using:

```text
is_staff = false
```

Conversion rate is calculated as:

```text
converted visitors / unique visitors
```

In the final verified run, the system produced:

```text
Unique visitors: 134
Converted visitors: 63
Conversion rate: 47.01%
```

## Funnel Logic

The `/stores/{store_id}/funnel` endpoint returns the customer journey:

```text
Entry → Zone Visit → Billing Queue → Purchase
```

Because the system uses multiple camera angles, the first funnel stage uses all unique non-staff visitor tokens instead of only raw `ENTRY` events. This avoids negative drop-off when zone cameras observe more tracked visitors than the entry camera.

Final verified funnel:

```text
Entry: 134
Zone Visit: 134
Billing Queue: 63
Purchase: 63
```

## Heatmap Logic

The `/stores/{store_id}/heatmap` endpoint calculates zone-level activity.

It returns:

* Zone visit count
* Average dwell time
* Normalized activity score from 0 to 100
* Data confidence flag

The normalized score helps the dashboard render which zones are hottest.

Example interpretation:

```text
MAIN_FLOOR = highest browsing activity
BILLING = queue and checkout activity
ENTRY_ZONE = entrance movement
```

## POS Conversion Logic

The POS CSV contains transaction rows but no customer identity.

The system handles this by generating `PURCHASE` events from billing queue visitors and POS transaction rows. This approximates the challenge rule that a visitor present in the billing zone shortly before a transaction can be counted as converted.

The script used is:

```text
pipeline/generate_purchase_events.py
```

It reads:

```text
data/all_events.jsonl
data/pos_transactions.csv
```

and writes:

```text
data/purchase_events.jsonl
```

Then the final event file is created by combining detection events and purchase events:

```text
data/final_events_with_purchases.jsonl
```

This final file is what should be ingested into the API for the complete analytics output.

## Dashboard

The live dashboard is implemented using Streamlit.

The dashboard calls the FastAPI endpoints and displays:

* Unique visitors
* Converted visitors
* Conversion rate
* Queue depth
* Average dwell per zone
* Funnel
* Heatmap
* Anomalies
* Health status

The dashboard can be started with:

```bash
streamlit run dashboard/streamlit_app.py
```

## Anomaly Detection

The `/stores/{store_id}/anomalies` endpoint detects operational issues.

Currently implemented anomaly:

```text
BILLING_QUEUE_SPIKE
```

This anomaly is returned when queue depth indicates billing pressure.

Example response:

```text
Severity: WARN
Suggested action: Open another billing counter or assign staff to billing area.
```

This makes the API useful not only for reporting metrics but also for operational action.

## Health Monitoring

The `/health` endpoint returns:

* API status
* Database connectivity
* Last event timestamp per store

This is useful for debugging and for an on-call engineer checking whether the event feed is stale or active.

Example verified output:

```text
status: ok
database: connected
last_event_timestamp_per_store: STORE_BLR_002
```

## AI-Assisted Decisions

AI tools were used during development to speed up system design, debug implementation issues, and evaluate trade-offs. The important part was not accepting every suggestion blindly, but testing outputs and modifying the approach based on actual results.

### 1. Detection Model Selection

AI suggested starting with YOLOv8 and ByteTrack instead of training a custom person detector.

I accepted this recommendation because the challenge focuses on building a complete working pipeline from raw CCTV footage to analytics APIs. Training a custom model would add complexity without guaranteeing better results in the available time.

YOLOv8 gave a strong practical baseline for person detection, and ByteTrack provided stable visitor tracking IDs for event generation.

### 2. Event Schema Design

AI helped structure a consistent event schema covering movement events, dwell events, billing queue events, and purchase events.

I kept the schema close to the challenge format because all downstream metrics depend on reliable event fields such as `event_id`, `visitor_id`, `event_type`, `timestamp`, `zone_id`, `dwell_ms`, `confidence`, and `metadata`.

The same schema is also used for POS-derived `PURCHASE` events, which makes ingestion simpler.

### 3. Camera-Wise Zone Configuration

The first implementation used one hardcoded set of zones. This failed because different CCTV cameras had different coordinate perspectives.

AI helped debug the mismatch by inspecting bounding box center coordinates. Based on that, I changed the design to use `data/camera_zones.json`, where each camera has its own zone definitions.

This made the pipeline more reliable across entry, zone, and billing cameras.

## Trade-Offs

### SQLite vs PostgreSQL

SQLite was chosen for local reproducibility and quick setup. It is enough for this take-home challenge and easy to inspect during debugging.

For production, PostgreSQL would be better because it supports concurrent writes, indexing strategies, larger storage, and stronger operational guarantees.

### JSONL Replay vs Kafka

The current event stream is implemented as JSONL files that are replayed into the API.

Kafka would be better for production event streaming, but JSONL replay is easier to run locally, easier to debug, and more suitable for a reproducible challenge submission.

The event schema is designed so the JSONL source can later be replaced with Kafka without changing the analytics API.

### Rectangular Zones vs Polygon Zones

The current implementation uses rectangular zones because they are simple and easy to debug.

Real stores often require polygon zones because camera perspectives are not perfectly rectangular. Polygon support would improve spatial accuracy and is a planned future improvement.

## Limitations

* Staff classification is not fully automated.
* Cross-camera re-identification is approximated through tracker-generated visitor IDs.
* Zone boundaries are rectangular instead of polygon-based.
* POS correlation is approximated by generating purchase events from billing queue visitors and POS rows.
* The system is optimized for local reproducibility rather than distributed production traffic.
* The current visitor IDs are reliable within camera tracks but not a complete person re-identification system across all camera views.
* Some zone boundaries were manually tuned using detected person center coordinates.

## Future Improvements

* Add polygon-based zone mapping
* Improve cross-camera Re-ID
* Add staff uniform detection
* Add billing queue abandonment logic
* Replace SQLite with PostgreSQL
* Add Kafka or Redis Streams for real-time event streaming
